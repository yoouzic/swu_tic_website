# SWU TIC 自动化审核与疑似假表研判系统设计

日期：2026-08-10

## 1. 背景与现状

`SWU_TIC-submit` 已经具备表单提交、分级人工审核、版本管理、课表核对、Excel 反馈表导入导出和批量自动审核入口。现有 `app/utils/auto_review.py` 同时承担 Excel 读取、通讯录匹配、全校课表核对、文本检查、批量状态推进和报告导出，职责过多，难以安全扩展。

现有批量自动审核会在发现问题后仍把表单推进到“部门已审核”或“中心已审核”。本设计改变这一自动决策边界：新系统只生成风险分类、证据和审核意见草稿，所有通过与驳回均由人工审核人执行。原有 `LectureForm.status`、审核权限、表单版本和评分语义保持不变。

本系统服务约 200 名技术部信息员，目标是通过确定性规则、课表冲突、历史异常模式和 DeepSeek 语义研判减少人工逐字段核对工作，同时保留完整证据链和最终人工决定权。

## 2. 已确认决策

- 采用现有 Flask 项目内的模块化单体扩展，不拆成独立微服务。
- 使用 Redis 和 Celery 执行持久化批量任务，替代应用内后台线程。
- 使用 DeepSeek 官方 OpenAI 兼容 Chat Completions API，默认模型为 `deepseek-v4-flash`。
- DeepSeek 可以接收当前完整表单及相关历史证据，包括个人信息；界面必须明确提示数据会发送给外部模型服务。
- 自动系统只分类和标记，不自动通过或驳回。
- 结果分为“无明显风险”“建议复核”“高风险疑似假表”“系统无法判断”四类。
- 规则在系统管理页配置，支持启停、风险等级、阈值、参数、版本和审计记录。
- 个人上课冲突采用“行政班基础推导 + 个人课表增强”的两级数据源。
- `demo` 中的真实历史数据只用于本地分析和验收，不提交 Git；自动化测试使用脱敏、合成的小型样例。

## 3. 目标与非目标

### 3.1 目标

- 自动核对表单字段、全校课表、行政班基础课表和个人课表。
- 支持常见错别字、文本格式、阈值和异常模式等可配置规则。
- 识别个人课表冲突、同学院听课、跨周重复见证人、连续周听同一教师和历史重复模式。
- 通过 DeepSeek 判断评价文本的合规性、具体性、模板化、矛盾和真实性疑点。
- 为每个结论保存规则、课表、模型和历史统计证据，便于人工复核。
- 支持至少 200 份表单的批量处理、进度查看、失败隔离、重试和幂等恢复。
- 与现有路由、权限、表单状态、审核版本、审核队列和视觉语言兼容。

### 3.2 非目标

- 不允许规则或模型直接通过、驳回或删除表单。
- 不用大模型代替精确课表匹配、数值计算或权限判断。
- 不建立通用低代码规则编程平台；复杂新规则仍需实现稳定的 Python 处理器。
- 不重写整个 `admin.py`、现有表单模型或人工审核流程。
- 不把 `demo` 真实数据、DeepSeek API Key、完整模型请求或敏感日志提交仓库。

## 4. 总体架构

```text
全校课表 ───────────────┐
行政班映射 ─────────────┼─> 课表标准化与版本化 ─┐
个人课表 ───────────────┘                      │
                                               ├─> 结构化证据包
待审核表单 ─> Celery 批次 ─> 确定性规则引擎 ───┤
历史最新版本 ────────────> 异常模式分析 ───────┘
                                                      │
                                                      ├─> DeepSeek V4 Flash
                                                      │
                                                      └─> 分类聚合器
                                                               │
                                                               v
                                             四类结果、证据、审核意见草稿
                                                               │
                                                               v
                                                     现有人工审核队列
```

核心原则是“代码提供客观证据，大模型完成语义研判，管理员作最终决定”。Celery 任务只传递数据库标识，不在 Redis 消息中携带完整表单或手机号；Worker 在已有权限和任务上下文中从数据库加载数据。

## 6. 数据模型

所有业务数据放入新增表，不给 `LectureForm` 添加或删除字段。

### 6.1 课表与映射

- `ScheduleDataset`：文件类型、学年学期、原文件名、SHA-256、导入人、导入状态、校验统计、是否当前启用及创建时间。
- `SchoolScheduleEntry`：课表版本、教师、教师学院、课程、教学班组成、专业组成、周次集合、星期、起止节次和地点。
- `ListenerClassMapping`：课表版本、信息员编号、学号、行政班和映射状态。
- `PersonalScheduleSlot`：课表版本、信息员编号或学号、课程、周次集合、星期和起止节次。

### 6.2 规则与版本

- `AutomationRule`：稳定规则键、名称、处理器类型、启用状态、默认风险等级和当前参数 JSON。
- `AutomationRuleRevision`：规则键、版本号、完整配置快照、修改人、修改原因和修改时间。

### 6.3 任务与结果

- `ReviewBatch`：Celery 根任务标识、发起人、状态、目标表单数、各分类数量、失败数、配置快照和时间字段。
- `ReviewAssessment`：表单版本、批次、四类结果、幂等指纹、模型标识、提示词版本、课表版本、规则版本、结构化模型结果和错误状态。
- `ReviewFinding`：审核结果、规则键、证据类型、风险等级、来源强度、原始值摘要、对比值摘要、解释和发生时间。

`ReviewAssessment` 的幂等指纹由规范化表单内容、表单版本、课表版本、规则版本、提示词版本和模型标识共同生成。相同指纹可以复用结果；任何依赖发生变化都会产生新的审核结果，不覆盖历史记录。

## 7. 课表数据与冲突检测

### 7.1 全校课表

导入器使用字段别名定位列，不依赖固定列号或 `max_column`。已知历史课表有 35 列，当前课表有 23 列，但均可映射到课程、教师、学院、教学班、专业、周次、星期、节次和地点等规范字段。

同一学期只允许一个启用的全校课表版本。新文件必须先完成校验预览，管理员确认后才切换启用版本；切换不会删除历史版本和历史审核依据。

### 7.2 行政班基础推导

管理员上传“信息员编号/学号 → 行政班”模板。系统根据规范化后的行政班与全校课表“教学班组成”建立基础课表。行政班推导可能遗漏选修课、跨专业课程和个人调课，因此其证据强度为 `approximate`。

仅由行政班推导得到的时间冲突，最高只能把结果提升为“建议复核”，不能单独产生“高风险疑似假表”。

### 7.3 个人课表增强

个人课表模板每行包含：学年学期、信息员编号或学号、课程、周次表达式、星期、起始节次和结束节次。至少一个身份字段必须能唯一解析到有效信息员。

个人课表与行政班推导结果取并集并去重。个人课表的精确时间重叠证据强度为 `exact`，可产生“高风险疑似假表”。覆盖状态显示为：

- `完整`：存在有效个人课表；
- `基础`：只有行政班映射；
- `缺失`：两类映射均不存在。

覆盖状态缺失只表示个人冲突维度无法判断，不阻塞全校课表、文本和历史规则继续运行。

### 7.4 时间标准化

系统统一解析教学周、星期和节次区间。冲突条件必须同时满足：同一学期、听课日期对应周次有效、星期相同且节次区间存在交集。历史日期格式先规范化；无法无歧义解析的数据进入导入校验报告，不能被默认为无冲突。

## 8. 规则框架与业务规则

每个处理器实现统一接口，返回零个或多个 `Finding`。规则不能直接修改 `LectureForm` 或提交数据库状态变更。

### 8.1 可直接在后台扩展的规则

后台可以新增并配置以下数据驱动类型：

- 错别字和易混词词典；
- 正则表达式和必需前缀；
- 字数、次数、比例和时间窗口阈值；
- 禁止值、允许值和字段组合条件；
- 重复次数与连续周次条件。

“的、地、得”等易混词只生成疑点和建议，不自动改写原文。复杂课表、跨表关联和统计规则通过注册新的 Python 处理器扩展，管理员仍可启停并调整其参数和风险等级。

### 8.2 已确认的初始业务规则

| 规则 | 默认分类影响 | 说明 |
| --- | --- | --- |
| 个人课表精确冲突 | 高风险疑似假表 | 周次、星期和节次均精确重叠 |
| 行政班推导冲突 | 建议复核 | 近似证据，不能单独升级为高风险 |
| 信息员与授课教师同学院 | 高风险疑似假表 | 违反“不能听自己学院老师课程”的规定；学院名称先做别名规范化 |
| 同一信息员跨教学周重复使用同一见证人 | 建议复核 | 不同信息员使用同一见证人允许；手机号为主要匹配依据，姓名与手机号组合用于确认 |
| 同一信息员在三周以上重复使用同一见证人 | 高风险疑似假表候选 | 需由分类聚合器结合其他证据确认升级 |
| 同一信息员连续两周听同一教师 | 建议复核 | 非连续周次不触发；表单重复版本先去重 |
| 课程反馈未以“该老师”开头 | 建议复核 | 这是填表规则，不是假表强证据 |
| 同一信息员同一时段存在不同听课记录 | 高风险疑似假表 | 排除同一表单的重复导出和版本记录后判断 |
| 课程、教师、学院、时间或地点与全校课表不一致 | 建议复核或高风险候选 | 风险由字段、匹配唯一性和证据组合决定 |
| 反馈少于 50 字、模板化或高度相似 | 建议复核 | 先排除同一表单的重复文件和版本 |

见证人匹配细则：同一手机号跨周出现视为重复身份强证据；姓名和手机号同时相同用于确认；同名不同手机号只作为弱证据；不同姓名共用同一手机号作为独立异常。见证人频率必须在“同一信息员”范围内计算，不能把不同信息员之间的正常复用直接判为异常。

## 9. 四类结果与聚合优先级

- `无明显风险`：关键数据可用，未命中中高风险规则，DeepSeek 也未发现明确疑点。
- `建议复核`：命中中等风险规则、存在近似课表冲突，或 DeepSeek 发现语义和合规疑点。
- `高风险疑似假表`：存在个人课表精确冲突、同学院听课、同一信息员同一时段多条不同记录等强客观证据；或者模型高风险判断同时获得至少一项客观证据支持。
- `系统无法判断`：关键依赖缺失或解析失败，且当前客观证据不足以形成其他分类。

客观强证据优先于模型状态。例如个人课表已确认精确冲突时，即使 DeepSeek 暂时不可用，结果仍为“高风险疑似假表”，并附加模型未完成的错误 Finding。DeepSeek 单独给出的高风险建议不能在没有客观证据时升级为“高风险疑似假表”。

无论分类为何，系统都不修改 `LectureForm.status`、`reviewer_id`、`review_time` 或 `review_comment`。人工审核人可将生成的意见草稿编辑后，通过现有审核接口提交最终决定。

## 10. DeepSeek 接入

默认环境配置：

```text
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_API_KEY=
DEEPSEEK_MODEL=deepseek-v4-flash
DEEPSEEK_THINKING=enabled
DEEPSEEK_TIMEOUT_SECONDS=60
DEEPSEEK_MAX_CONCURRENCY=4
```

模型名称和基础地址保持可配置，以便官方模型迭代时无需修改业务代码。DeepSeek 官方文档确认 `deepseek-v4-flash` 支持 OpenAI Chat Completions、思考模式和 JSON 输出：

- https://api-docs.deepseek.com/api/create-chat-completion
- https://api-docs.deepseek.com/quick_start/pricing/

每次请求包含当前完整表单、规范化课表对比、规则证据、历史统计和必要的相似文本片段。历史数据以相关摘要为主，不把无关的其他信息员完整记录加入上下文。

模型响应必须通过固定 JSON Schema 校验，字段包括：

```json
{
  "compliance": "compliant | questionable | non_compliant | unknown",
  "authenticity": "credible | questionable | high_risk | unknown",
  "suggested_classification": "no_obvious_risk | review_recommended | high_risk_suspected_fake | unable_to_determine",
  "confidence": 0.0,
  "issues": [],
  "evidence_refs": [],
  "review_draft": ""
}
```

非法枚举、缺失字段、证据引用不存在或无法解析的响应均视为失败，不使用自由文本猜测补全。API Key 只从环境变量读取；普通日志不记录 Authorization、完整请求、完整响应、手机号或签名。数据库保存结构化结果、必要证据和请求内容哈希，不复制保存一份完整请求正文。

## 11. Celery 批处理与故障处理

批次状态为 `queued`、`running`、`partial`、`succeeded`、`failed` 或 `cancelled`。一个根任务拆分为单表任务和聚合回调，单表失败不回滚其他结果。

- 429、超时、连接错误和 5xx 使用带抖动的指数退避重试。
- 400、401、403、无效模型名和 JSON Schema 配置错误不进行无意义重试，并暂停同批次后续模型请求。
- Redis 或 Worker 重启后，未确认任务可以重新投递；幂等指纹避免重复结果。
- 管理员可以重跑失败项或因依赖变化而失效的结果。
- 取消只阻止尚未开始的任务；正在处理的单表任务安全完成并保存结果。
- DeepSeek 不可用时确定性规则继续运行，系统不得把缺少模型结论的表单标记为“无明显风险”。

## 12. 管理界面与人工流程

### 12.1 系统管理页

“自动审核”区域提供：

- Redis、Celery Worker 和 DeepSeek 配置状态；
- 全校课表上传、预览、启用和历史版本；
- 行政班映射模板下载、上传和覆盖统计；
- 个人课表模板下载、上传、错误报告和覆盖统计；
- 规则列表、启停、参数编辑、风险等级、修改原因和历史版本；
- 批次列表、实时进度、分类统计、失败项、重试和取消；
- DeepSeek 模型名称和 API Key 是否已配置，永不回显密钥正文。

### 12.2 审核队列

现有审核队列增加：

- 四类风险筛选、风险标签和课表覆盖状态；
- 批量审核预览，包括可处理、缓存复用、行政班基础覆盖、个人课表完整覆盖和缺失数量；
- 证据抽屉，分为课表冲突、业务规则、文本问题、历史模式和 DeepSeek 研判；
- 每条 Finding 的规则来源、原始值摘要、对比值摘要、证据强度和时间；
- 可编辑的人工审核意见草稿。

交互继续使用 Bootstrap 模态框、offcanvas、`aria-live` 和局部 DOM 更新，不使用 `alert`、`confirm`、`prompt`、`window.open`、内部 `_blank` 或整页刷新。

### 12.3 权限

- 超级管理员可以管理课表、映射、规则和服务设置。
- 具有“审表_中心”权限的管理员可以发起和查看全中心批次。
- 结果可见范围继续由现有表单查看权限决定，自动审核接口不能扩大数据范围。
- 规则修改、课表启用、任务发起、重试、取消和最终人工审核均记录操作人和时间。

## 13. 真实历史数据带来的导入约束

本地 `demo` 目录包含 79 个工作簿。只读审计识别出 75 个反馈表、354 行原始记录；按完整记录指纹去重后为 285 条、38 名信息员。该样本不能代表全部 200 名信息员，但足以验证历史格式兼容和重复导出问题。

必须处理以下已观察情况：

- 反馈表主业务字段位于 B:Y，字段行通常为第 2 行，后面可能存在后勤反馈等其他区域。
- 15 个工作簿因格式残留将使用范围扩张到 198 列，不能使用 `max_column` 判定业务结构。
- 7 个工作簿包含额外工作表，导入器必须明确选择反馈表和主表区域。
- 部分文件无法由常规解析器读取，批量导入必须按文件隔离错误并输出报告。
- 同一表单会出现在单组、合并和审核后工作簿中；所有跨记录统计必须先按规范化记录指纹去重。
- 严格日期格式下存在历史变体；系统应规范化可无歧义解析的格式，对其余记录给出行级错误。
- “该老师”是正式填表前缀规则，不能因其高频而认定为模板异常。
- 审核前后样本实际修改过课件质量、地点和评价文本，系统应提供字段级证据和建议，但不得覆盖原始内容。

`demo` 位于 Git 仓库外。测试夹具只保留字段结构和被验证的边界行为，所有姓名、编号、学号、手机号、签名、原始评价和具体课程组合均替换为合成数据。

## 14. 数据安全与外部传输

管理员发起包含 DeepSeek 的审核前，界面明确提示完整表单及相关证据会发送到 DeepSeek 外部 API。该传输范围是本设计已确认的业务选择。

- API Key 只通过部署环境注入。
- Celery 消息只包含数据库 ID、批次 ID 和任务控制参数。
- 应用日志使用结构化错误码和任务 ID，不记录完整请求正文。
- 下载的错误报告默认遮蔽手机号和学号，只显示行号和错误类型；超级管理员在受控详情中查看原始行。
- 模型供应商的数据处理与保留受其服务条款约束，系统界面和部署文档必须提醒管理员确认校内数据合规要求。

## 15. 数据库初始化与兼容迁移

当前项目没有 Alembic 迁移链。实现提供幂等 Flask CLI 初始化命令，只创建自动审核新增表和索引，不修改现有表。启动前先在数据库备份副本上执行并验证；回滚步骤是停止 Worker、禁用新入口并保留新增表，不能删除已有审核结果。

兼容要求：

- 旧自动审核、设置、上传、下载和状态路由保持可解析。
- 现有表单字段、登录字段、角色、权限和审核状态名称不改变。
- 现有人工审核继续创建或更新原有表单版本，自动评估只作为旁路数据。
- 旧 Excel 反馈表入口可以继续导入，不要求历史文件先转换为新模板。

## 17. 设计总结

本设计在现有 SWU TIC 审核流程旁增加可审计的自动研判层。确定性规则负责客观事实，DeepSeek V4 Flash 负责语义合规与真实性疑点，四类聚合器负责一致分类，人工审核人保留唯一最终决定权。行政班映射为 200 名信息员提供快速基础覆盖，个人课表补充选修和个性课程；真实历史数据用于验证格式兼容，但不会进入 Git 或普通日志。
