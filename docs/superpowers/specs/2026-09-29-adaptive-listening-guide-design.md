# 自适应问答式听课助手设计

状态：已获用户确认，2026-09-29。

## 1. 背景与问题

当前第一阶段实现已经具备课表索引、候选搜索、备用来源、冲突确认、服务端复核和证据留痕，但用户界面仍接近“另一个填表”：用户先填写日期、教室、教师和学期，再浏览候选卡片。

原始设想是“像助手提问一样逐步锁定课程”：系统根据已有信息每次只问一个问题，用户通过 A/B/C 选项或 D 自定义回答逐步缩小候选范围。现有服务层应保留为可靠的候选与复核基础，前端交互和问答编排需要调整。

历史回测结果为候选召回 273/300（91.00%），独立字段完全一致 27/32（84.38%），没有达到 95%/99% 的自动化门槛。因此“锁定”只表示候选足够明确后请求用户确认，不能自动把推荐结果当作事实。

## 2. 目标

1. 所有 active、已认证用户都能进入同一套课程识别向导。
2. 初始界面先问“你还记得什么”，而不是展示一组完整表单输入框。
3. 每轮只呈现一个问题，最多展示三个最有区分度的选项，并提供 D“我自己填写/自定义回答”。
4. 根据用户已知信息和当前候选集合动态决定下一问，默认最多三轮信息问题，存在歧义时允许第四轮。
5. 候选足够明确后展示课程、教师、教室、班级和具体节次，由用户确认后才补充正式表单。
6. 始终保留“不是这些”“返回上一步”“手动填写”和冲突确认路径。
7. 继续使用现有权威课表、备用课表、服务端重新验证和证据记录。

## 3. 非目标

- 本阶段不引入自由聊天式大模型解析。
- 不把教师/督导伪装成信息员，不复用学生签名、电话或学生专用评价字段。
- 不删除现有直接填写表单和已有候选 API。
- 不自动提交表单，不自动确认课程，不绕过人工确认。
- 不因为历史回测未达门槛而宣称问答流程可以达到 100% 正确。

## 4. 用户交互

### 4.1 初始问题

向导第一屏只显示：

> 你还记得哪类信息？

- A：听课日期
- B：授课教师
- C：教室
- D：其他信息，我自己填写

用户选择后进入对应的单字段回答界面。D 不是无约束聊天入口，而是针对当前问题的可验证自定义输入：日期使用日期控件并允许有限格式文本，教师支持搜索和文本输入，教室支持选项和文本输入，节次使用节次按钮并允许“第3-4节”格式。

### 4.2 动态问题选择

服务器或纯服务层维护 known_facts、candidate_ids、asked_question_kinds 和 question_count。每轮从可用问题类型中选择：

1. 能最大幅度减少当前候选集合的字段；
2. 用户容易判断的字段；
3. 还没有被问过、且不是由当前冲突产生的重复字段。

问题类型至少包括 date、teacher、room、period、student_grade_class。系统可以根据已有事实跳过不必要的问题，例如已明确教室且候选只有一门课时不再询问教师。

每轮 A/B/C 选项从当前权威候选中动态生成，按区分度和稳定排序选出最多三项。D 始终进入该问题的自定义输入。选项不足三个时不填充虚假选项。

### 4.3 停止与确认

- 当前候选集合只有一个、且没有未处理冲突：进入“确认这节课”。
- 当前候选集合有二至三个：以 A/B/C 形式让用户选择课程候选，D 允许自定义纠正。
- 当前候选仍多于三个：继续提问，直到达到问题预算或出现有效区分字段。
- 默认最多三轮信息问题；如果仍存在可解释的歧义，允许第四轮。
- 第四轮后仍无法唯一化时，展示候选与手动填写，不继续追问。
- 任何情况下仍提供“都不是/这些都不对”，包括只有一个候选时。

确认卡必须显示来源、具体节次、教室、教师和冲突提示。备用来源必须显示“备用课表线索 · 需核对”，并要求来源确认。服务端重新搜索并验证 candidate_id、来源批次、学期、覆盖值和冲突处理后，才允许把字段快照补入现有表单。

## 5. 状态与数据边界

建议新增纯数据合同：

    GuidedAssistantState(
        known_facts: Mapping[str, str],
        candidate_ids: tuple[str, ...],
        asked_question_kinds: tuple[str, ...],
        question_count: int,
        stage: Literal['question', 'candidate', 'confirm', 'manual', 'done'],
    )

    GuidedQuestion(
        kind: str,
        prompt: str,
        options: tuple[GuidedOption, ...],  # 0-3 个
        allow_custom: bool,
        custom_label: str,
    )

客户端可以暂存问答状态和展示历史，但不能把客户端候选快照当成事实。每次回答都使用已知事实重新查询当前权威来源；确认仍复用既有 revalidate_selection()。

现有 AssistantQuery、Candidate、ListeningAssistantService、ListeningAssistantEvidence 和 /confirm 作为底层边界保留。问答编排只决定“下一问是什么”和“如何展示选项”，不复制课程匹配规则。

## 6. API 方向

新增问答编排端点：

- POST /user/api/listening-assistant/guide/start
  - 输入可选的现有表单/草稿事实；
  - 返回初始 GuidedQuestion 和空会话状态。
- POST /user/api/listening-assistant/guide/answer
  - 输入上一轮状态、问题类型和回答；
  - 服务端规范化回答、重新加载权威候选，并返回下一轮问题、候选摘要或确认状态。

端点必须限制字段白名单、限制问答历史长度、拒绝未知问题类型和越界问题计数，并返回统一 {success, data, message}。客户端状态只是传输载体，最终确认不信任它。

已有候选、备用和确认端点继续保留，供旧入口、手动兜底和渐进迁移使用。

## 7. 身份与提交

问答体验可以对所有 active、已认证用户开放，但课程确认后的提交必须由 SubmissionProfile 或现有角色模板决定。第一阶段仍只把确认结果接入现有信息员 LectureForm 流程；教师/督导模板另行设计。

## 8. 验收标准

- 空状态进入后首先看到“你还记得哪类信息”，而不是四个并列基础输入框。
- 每轮只有一个主要问题，A/B/C 来自当前候选，D 能打开针对当前字段的自定义输入。
- 至少验证日期、教师、教室、节次四种问题类型的动态跳转。
- 三轮信息问题可以进入候选/确认；第四轮只在仍有可区分字段时出现。
- 单候选和多候选都能选择“都不是”。
- 备用课表、冲突、来源确认、人工覆盖和服务端重新验证规则保持不变。
- 用户返回或修改上一轮回答后，后续候选和问题会被清空并重新计算。
- 问答历史、草稿和提交证据不包含电话、签名、凭据或原始评价文本。
- 现有直接填写表单、旧草稿、版本和提交事务回归测试继续通过。
- 浏览器验收覆盖 A/B/C/D、键盘操作、移动宽度、XSS 文本显示和 console error；缺少真实浏览器环境时必须明确报告 NOT_RUN/BLOCKED。
